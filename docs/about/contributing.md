# 贡献指南

一条赏析的编辑成本很低，但**质量下限必须统一**。这一页是那个下限。

## 一条赏析的字段

在 `docs/.vitepress/data/notes.json` 里，以帧的 `id` 为键添加：

```json
"1.9-179": {
  "reading": "赏析正文，150–300 字",
  "device": "手法，一个短语",
  "basis": "text",
  "tags": ["牺牲", "留白"]
}
```

| 字段 | 要求 |
|---|---|
| `reading` | 主体。写「这句话在做什么」，不是复述剧情。150–300 字，超过 400 字说明你想说的不止一件事，拆成两条 |
| `device` | 一个短语，命名这句话用的手法。已有：尺度落差、语体错位、主语省略、矛盾修辞、元叙事、动词递进、悬置判断、褒词贬用、碑文式语序 |
| `basis` | `text`（只靠这句话和标题就能论证）或 `plot`（需要剧情背景）。**拿不准就用 `plot`** |
| `tags` | 1–3 个主题词。优先复用已有标签，不要为一条句子新造一个只出现一次的词 |

## 三个自检问题

写完先问自己：

**1. 这句话的力度来自哪里？**
如果你说不出具体来源（是措辞？是省略？是前后对比？），说明你只是觉得它好听。觉得好听不是赏析。

**2. 换一个人读这句原文，能得到同样的结论吗？**
如果只有读过某章剧情的人才能理解你在说什么，那这条应该是 `plot`，而且要把必要背景写进 `reading`。

**3. 我是不是在替文案组解释？**
「文案想表达的是……」是最常见的写法，也是最空的一种。除非有官方访谈佐证，否则写「这句话做了 X」，不要写「作者想表达 Y」。

## 三种要避免的写法

**❌ 复述剧情当赏析**

> 这句话出现在维尔汀与某角色对峙之后，她终于明白了一切，于是说出了这句台词。

——这不是赏析，是复述。读者已经知道剧情，他要的是**为什么这么写**。

**❌ 形容词堆砌**

> 这句话非常优美、极具张力、深刻动人，令人久久不能平静。

——删掉这些词，什么也没少。

**❌ 过度解读**

> 这句话暗示了第三个势力的存在，并为后续版本埋下伏笔。

——如果不是官方明确写过，这就是编。**编造的解读比没有解读伤害大得多**，因为它会被当真。拿不准的判断就标 `plot`，并在 `reading` 里写明这是推断。

## 标签的扩展规则

已存在的标签优先复用。确实需要新标签时：

1. 检查[句子墙](/quotes)上的现有标签，确认语义不重叠（例如已有「失去」，就不要加「丧失」）
2. 新标签至少要能覆盖**三条以上**候选句子才值得建立
3. 标签是**主题**或**手法**，不是评价。「写得好」「神作」不是标签

## 提交流程

```bash
# 1. 只改 data 目录，不改组件
git checkout -b note/1-9-179
# 编辑 docs/.vitepress/data/notes.json

# 2. 本地验证：起服务，确认这一条渲染正常
npm run dev

# 3. 提交
git commit -m "note(1.9): 结与解·二 —— 神话尺度与五个字的落差"
```

**一次 PR 只做一类事**：要么加赏析，要么补数据，要么改代码。混在一起没法审。

## 补帧数据

`cg.json` 的字段：

| 字段 | 说明 |
|---|---|
| `id` | `{版本}-{全局编号}`，如 `1.9-179`。编号沿用社区整理的全库顺序，不要自行重排 |
| `no` | 全局编号，整数 |
| `chapter` | 章节 id，对应 `chapters.json` 的 `id`（`ch-01` …） |
| `zh` / `en` | 中文标题 / 英文标题，**照录，不要改写** |
| `text` | 点睛文案原文。标点统一为中文全角，其余照录 |

补数据时如果**不确定版本号**，就填 `null` 并在 `chapters.json` 里把 `versionVerified` 设为 `false`。页面会自动显示「版本待核」——这是被允许的状态，不是缺陷。
